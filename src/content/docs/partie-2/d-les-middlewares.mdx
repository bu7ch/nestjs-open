Tu as déjà utilisé un middleware sans le nommer : `express.json()`, en section c. Un **middleware** est une fonction `(req, res, next)` placée entre la requête et ta route : elle peut lire ou modifier `req`, répondre directement, ou passer la main à la suite avec `next()`.

```js
function journal(req, res, next) {
	console.log(`${req.method} ${req.url}`);
	next();
}

app.use(journal);
```

`app.use(middleware)` l'applique à **toutes** les requêtes, dans l'ordre où tu l'ajoutes — place `journal` avant tes routes, sinon les requêtes traitées avant lui ne seront jamais journalisées. Un middleware qui oublie d'appeler `next()` (et de répondre) laisse la requête bloquée indéfiniment.

## Un middleware sur une seule route

Passé en deuxième argument d'une route, un middleware ne s'applique qu'à elle :

```js
function exigerPseudo(req, res, next) {
	if (!req.headers['x-pseudo']) {
		res.status(400).json({ message: "En-tête x-pseudo manquant" });
		return;
	}
	next();
}

app.post('/api/villages', exigerPseudo, (req, res) => {
	// req.headers['x-pseudo'] existe forcément ici
});
```

## Une route qui n'existe pas

Un dernier `app.use`, placé après toutes tes routes, rattrape tout ce qui n'a matché aucune d'elles :

```js
app.use((req, res) => {
	res.status(404).json({ message: 'Route inconnue' });
});
```

Il doit être en dernier : Express essaie chaque route et chaque middleware **dans l'ordre d'écriture**, et s'arrête au premier qui répond.

Tu retrouveras ce principe sous d'autres noms : les *pipes* (partie 4), les *guards* (partie 7) et les *interceptors* de NestJS sont, eux aussi, du code qui s'intercale entre la requête et ta route — en plus structuré, et déclaré avec des décorateurs plutôt qu'avec `app.use`. La partie 8 les met tous côte à côte, avec les middlewares, et te montre dans quel ordre ils s'exécutent.
